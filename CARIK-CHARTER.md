# The Dwi-Tunggal Charter — Universal File-Over-App & Reasoning-Over-Mechanic Doctrine

## 1. Preamble: The Two Pillars

Knowledge work, creative synthesis, and complex systems architecture conducted collaboratively between humans and artificial intelligence require a durable foundation that resists technological decay and cognitive distortion.

The architecture rests upon two co-equal, interdependent foundational pillars known as the **Carik Charter**:

```text
┌─────────────────────────────────────────────────────────────────────────────┐
│                             CARIK CHARTER                                   │
├──────────────────────────────────────┬──────────────────────────────────────┤
│ 1. FILE-OVER-APP                     │ 2. REASONING-OVER-MECHANIC           │
├──────────────────────────────────────┼──────────────────────────────────────┤
│ Plain text files are permanent stone │ Truth is established exclusively by  │
│ hieroglyphs owned by the human.      │ dialectical human-agent reasoning.   │
│ Software, agents, and harnesses are  │ Tools verify formal storage hygiene; │
│ temporary, replaceable chisels.      │ reasoning governs domain substance.  │
│ Data is never held hostage by code.  │ Tools must adapt, never the reverse. │
└──────────────────────────────────────┴──────────────────────────────────────┘
```

Both pillars are load-bearing and mutually necessary:
- **Without File-Over-App**, creative and analytical work is held hostage by proprietary vendor silos, opaque binary databases, and ephemeral model context windows.
- **Without Reasoning-Over-Mechanic**, automated software tools invert their role from humble instruments of order into authoritarian censors that police substantive thought.

---

## 2. Pillar 1: The File-Over-App Principle

The architecture adheres unconditionally to the **file-over-app philosophy** ([Steph Ango, 2023](https://stephango.com/file-over-app)): software applications, platforms, and AI models are ephemeral tools (chisels), whereas the durable artifact is a human-readable file you control and own (hieroglyphs carved in stone).

### Core Axioms

1. **Durable Across Decades:** Any repository or vault built on this charter must remain fully functional, readable, and editable across decades (from 1960s to 2060s+) as plain text opened directly in simple text editors, terminal environments, or decentralized version control.
2. **Zero Proprietary Lock-In:** Project canon, analytical records, domain models, and primary artifacts must reside in standard text files—never inside proprietary SaaS databases, cloud-locked platforms, binary blobs, or model-memory caches.
3. **Open Formats Only:**
   - **Markdown (`.md`):** The primary medium for human and agent thought, analytical dossiers, structured ledgers, and narratives, governed by clean, parseable YAML frontmatter.
   - **Open Visual Standards (e.g. `.canvas`, `.svg`):** Open specifications for graphs, mind maps, and spatial boards that can be parsed as plain text without specialized application runtimes.
   - **Structured Interoperability (`.json`, `.yaml`):** Confined strictly to deterministic machine-to-machine schemas, pipeline dependency graphs, and ledger manifests.
   - **Domain-Specific Open Text:** Any specialized deliverable must use an open, human-readable text standard (e.g. `.fountain` for screenplays, `.tex`/`.bib` for academic papers, source code files for software engineering).
4. **Independent Filesystem Reality:** A vault's truth is defined by files residing physically on disk. Virtual abstractions, database indexes, or in-memory caches are strictly derived secondary projections and hold zero authority over the filesystem.
5. **No Mandatory Runtime Daemons:** Navigating, inspecting, reading, or editing the repository requires no background database process, Node.js server, compiler pipeline, or continuous daemon. Helper scripts assist the user but are never a prerequisite for accessing project truth.

## 3. Pillar 2: The Reasoning-Over-Mechanic (ROM) Doctrine

### 3.1 The Historical Context: The Pre-LLM Trap

Before Large Language Models, automated systems were fundamentally incapable of comprehending semantic context, narrative causality, or nuance. System designers compensated by constructing rigid regular expressions, keyword linters, and compiler-style Abstract Syntax Tree (AST) assertions.

When these mechanistic patterns are unthinkingly applied to creative writing, qualitative research, or architectural design, they create a destructive **Compiler-over-Substance Inversion Trap**:
- Automated scripts police natural language prose as if it were strict C++ or Rust code.
- Brittle heuristics—such as word-count quotas, vocabulary restrictions, rigid section counts, or forbidden tokens—are elevated into automated gatekeepers (`exit code 1` or unhandled exceptions).
- AI agents are degraded from collaborative reasoning partners into sycophantic, defensive chatbots that waste cognitive bandwidth satisfying arbitrary syntactic rules, frequently refusing sound human decisions because "the validator would fail."

### 3.2 The Doctrine Codified

The **Reasoning-Over-Mechanic** doctrine re-establishes the rightful boundary between tools and human intellect:

> *"Automated scripts, linters, and harness tools function strictly as instruments of formal hygiene—not judges of truth. They organize work so it remains orderly; they do not measure substance or validity. When a tool conflicts with human-agent reasoning, the reasoning is presumed correct and the tool is flawed. Tools can and must be edited, adapted, or dismantled to serve reasoning."*

Whenever a contradiction arises between an author-approved domain decision and a validator script:
1. **The author's decision carries an absolute presumption of correctness.**
2. **The script is obsolete, overly rigid, or incomplete.**
3. **The script must adapt, yield, or be removed to serve the work, never the reverse.**

## 4. Demarcation of Authority: Formality vs. Substance

To permanently prevent regression into semantic policing, the harness enforces an absolute, binary division of authority:

```text
┌─────────────────────────────────────────────────────────────────────────────┐
│                           DIVISION OF AUTHORITY                             │
├──────────────────────────────────────┬──────────────────────────────────────┤
│ FORMALITY (Owned by Tools / Scripts) │ SUBSTANCE (Owned by Reasoning)       │
├──────────────────────────────────────┼──────────────────────────────────────┤
│ • Physical file existence on disk    │ • Domain causality & systemic logic  │
│ • Valid YAML frontmatter parsing     │ • Qualitative truth & thematic depth │
│ • Unbroken internal wikilinks        │ • Rhetorical friction & moral choice │
│ • File naming & directory structure  │ • Aesthetic style, tone, & diction   │
│ • Mathematical bounds (e.g. budgets) │ • Conceptual necessity & subtraction │
│ • Repository write boundary guards   │ • Ethical, creative, & domain choices│
├──────────────────────────────────────┼──────────────────────────────────────┤
│ Tool Behavior:                       │ Reasoning Behavior:                  │
│ Fast, deterministic, hard blocker on │ Dialectical, probabilistic, and      │
│ storage corruption or boundary leak  │ collaborative; audited by panels     │
└──────────────────────────────────────┴──────────────────────────────────────┘
```

### The Universal Litmus Test

When determining whether any proposed check belongs inside an automated script or within dialectical human-agent reasoning, apply the **Universal Litmus Test**:

> *"Does this check remain valid if the project's named entities, physical setting, historical era, and specific subject/genre are swapped?"*
>
> - If **YES** $\rightarrow$ It is **Formality** (structural hygiene). Eligible for Class C automated checking and blocking.
> - If **NO** $\rightarrow$ It is **Substance** (qualitative domain truth). Strictly forbidden from automated blocking; owned exclusively by human-agent reasoning.

### The Formality Reporting Boundary

A formality checker may report what it observed; it may not conclude what it did not observe:
- **Permitted:** Reporting that a specific directory or declaration key is absent on disk.
- **Prohibited:** Concluding that the project is conceptually obsolete, structurally defective, or architecturally invalid based solely on that absence.
- Absence of evidence licenses no conclusion. When an automated tool cannot find a positive marker, it must return an absence of classification (`null` / `UNDETERMINED`), never an invented negative verdict.

## 5. The Three-Tier Action Taxonomy

Every validation routine, script, hook, and automated check in the repository must be assigned to **exactly one** of three classes:

```text
┌─────────────────────────────────────────────────────────────────────────────┐
│                        THREE-TIER ACTION TAXONOMY                           │
├─────────────────────────────────────────────────────────────────────────────┤
│ CLASS A: AMPUTATE (Deleted)                                                 │
│ Eliminates semantic policing, word quotas, vocabulary bans, and verbatim    │
│ cross-file equality assertions. Zero tolerance for Class A code.            │
├─────────────────────────────────────────────────────────────────────────────┤
│ CLASS B: ADVISORY HEALTH CHECKS (Exit Code 0)                               │
│ Emits actionable structural diagnostics, style hints, and debt warnings.    │
│ NEVER blocks progression. Tool prints report and exits with 0.              │
├─────────────────────────────────────────────────────────────────────────────┤
│ CLASS C: PHYSICAL INTEGRITY HARD BLOCKERS (Exit Code 1)                      │
│ Confined strictly to storage hygiene, unparseable syntax, broken links,     │
│ acyclic pipeline graphs, physical ceilings, and repository write boundaries.│
└─────────────────────────────────────────────────────────────────────────────┘
```

1. **Class A — Amputated Semantic Policing (Excised):**
   Routines that attempt to measure quality, correctness, or meaning through literal strings. These are completely eliminated.
2. **Class B — Diagnostic Advisories (Exit Code 0):**
   Tools that provide structural visibility, identify unreferenced records, flag potential inconsistencies, or surface lint warnings. They inform reasoning but confer zero programmatic blocking power. The exit code is always `0`.
3. **Class C — Physical Integrity Blockers (Exit Code 1):**
   Strict, deterministic guards confined to protecting storage durability, file-over-app integrity, and safe execution:
   - Malformed YAML frontmatter or unparseable syntax.
   - Missing physical files declared as mandatory inputs in the pipeline graph.
   - Broken internal links preventing graph traversal.
   - Cyclic dependency errors in pipeline manifests.
   - External boundary violations (preventing unapproved writes outside the vault root).
   - Absolute physical resource ceilings (e.g. file size, hard page/line ceilings).
   *Failure in Class C represents data corruption or boundary breach—never an artistic or substantive disagreement.*

## 6. Creative Sovereignty Credo

To prevent tools or existing artifacts from obstructing ongoing work, all agents and contributors are bound by five universal operational laws:

1. **Documents Are Soft Law:** Working documents, design specs, and ledgers record the minutes of the *last* decision. They are never scripture to defend against today's work.
2. **No Document Worship:** An agent must never argue "this cannot be done because document X says otherwise." The proper posture is active tracing: identify downstream consequences, propose the adaptation cascade, and present the resulting work to the human.
3. **Mandatory Adaptation Cascade:** Changing a core fact or decision triggers a cascade across dependent files. Systemic consistency is maintained by chasing changes downstream, not by resisting them at the point of origin.
4. **Presumption of Correctness & Adversarial Duty:** The project owner's substantive domain decisions carry an absolute presumption of correctness. However, agents are strictly forbidden from sycophantic compliance: an agent must verify premises against primary evidence before acting, and must proactively surface risks and contradictions through the Four Doors of Challenge before execution.
5. **The Four Doors of Challenge:** An agent may and must challenge an owner's substantive direction when it trips one of four explicit evidentiary doors:
   - *Door 1: Active Basis Violation* (contradicting an immutable foundational constraint or verifiable public record in adapted work).
   - *Door 2: Core Purpose Destruction* (demonstrably destroying the project's primary utility, tension, or stated goal).
   - *Door 3: Concrete Internal Contradiction* (citable conflicts between physical entities, established facts, or timestamps).
   - *Door 4: Universe / System Logic Contradiction* (violating the internal rules established by the project's own declared canon or physics).
   *Automated scripts, linters, and validator schemas do NOT constitute a door of challenge; tools must yield to verified human reasoning.*

## 8. Summary: The Sustainable Working Posture

Under the Carik Charter:
- **Files** remain the permanent home of human thought, readable without specialized software across generations.
- **Tools** remain obedient, fast, and subordinate instruments of hygiene that maintain order without judging truth.
- **Humans and AI Agents** operate as collaborative intellectual partners—analyzing, designing, and iterating through principled dialectical reasoning.
